# MediaFleet 扩展开发指南

本文回答“新增一种能力时应改哪里、还需要同步什么”。开始前先阅读
[总体架构](../architecture/overview.md)和[服务边界](../architecture/service-boundaries.md)。

## 1. 通用开发流程

1. 执行 `git status --short --branch`，保留已有工作。
2. 从 `docs/project-status.md` 确认当前阶段和第一个未完成事项。
3. 确定能力归属和持久状态，画出请求、数据库、消息、执行者和结果的完整链路。
4. 如果修改消息或 API 契约，先搜索并列出全部生产者、消费者和兼容入口。
5. 在一个清晰的服务边界内完成最小闭环，再扩展其他入口。
6. 添加与风险相称的单元、契约、边界或集成测试。
7. 更新架构文档和 `docs/project-status.md`。

## 2. 新增通用媒体任务

适用于任意等价 Worker 都能执行的任务，例如新的转码、截图或音频分析。

1. 定义稳定 `task_type`、参数和结果结构，明确是否可重试、是否需要幂等键。
2. 在 `services/media_worker/processors/` 下实现处理器，避免让处理器直接承担 RabbitMQ 生命周期。
3. 在 `services/media_worker/registry/processor_registry.py` 注册处理器。
4. 复用任务执行服务的领取、租约、状态迁移、结果保存和错误分类。
5. 在控制中心 API 中通过 `TaskDispatchService` 创建持久任务，不直接发布裸消息。
6. 为处理器、注册表、执行状态和消息契约添加测试。

如果新任务依赖只有部分实例具备的 GPU、模型或外部运行时，不能继续绑定到所有实例共享的
`media-worker.tasks`。应设计独立能力队列、路由键、健康能力上报和部署说明。

## 3. 新增录制节点命令

适用于必须在录像文件所有者节点执行的操作。

1. 在 `RecorderCommandType` 中定义命令并评估契约版本兼容性。
2. 在控制中心先持久化命令意图、目标节点和稳定 `message_id`。
3. 扩展录制命令发布服务，路由到 `recorder.<node_id>`。
4. 在 `services/recorder_node/commands/` 注册处理器，校验目标节点与当前节点一致。
5. 明确重复消息的幂等行为、可恢复错误、永久错误和 DLQ 处理方式。
6. 同步生产者、消费者、契约测试、恢复测试和本文档。

摄像头拉流和断流仍由 RTC 或客户端在取得绑定后调用 ZLMediaKit；不要把所有 ZLMediaKit
操作都无条件塞入录制命令通道。

## 4. 新增内容分析流程

适用于长耗时、大模型调用、文档解析或需要分步检查点的任务。

1. 保持 `CONTENT_ANALYSIS` 投递通道和独立队列。
2. 将提示词和步骤定义版本化，执行记录保存所用版本。
3. 每个可恢复步骤完成后持久化检查点，重启时从最后成功步骤继续。
4. 外部模型调用设置明确超时、有限重试和输入大小限制。
5. 日志不得记录 API Key、完整敏感文档或签名下载 URL。

## 5. 新增 REST API

- Pydantic 模型负责输入输出契约，路由函数保持薄层。
- 应用服务负责用例，仓储负责数据库访问，消息发布器负责传输。
- 写接口应接受或生成幂等键；长任务立即返回任务 ID。
- 新 API 同时补充 OpenAPI 摘要、错误语义、授权要求和 API 测试。
- 如果旧兼容 API 也需要新行为，让两者调用同一应用服务，不复制业务逻辑。

## 6. 新增持久化字段或表

1. 修改 SQLAlchemy 模型和相应仓储。
2. 新建 Alembic 迁移，说明升级、数据回填和回滚策略。
3. 多实例部署中由独立发布步骤执行迁移，不能让所有控制中心并发执行 DDL。
4. 对状态字段使用条件更新，避免最后写入者覆盖新状态。
5. 配置默认值时区分数据库默认值、应用默认值和历史数据回填。

## 7. 新增独立服务的判断条件

只有同时满足多个条件时才建议新建服务：

- 依赖或运行时与现有服务明显冲突；
- 资源模型和扩缩容方式独立；
- 故障隔离有明确收益；
- 有稳定输入输出契约和持久恢复策略；
- 运维团队可以独立部署、监控和升级它。

新服务至少需要入口、健康检查、配置示例、Dockerfile、Compose 示例、消息或 REST 契约、
日志脱敏、优雅停机、基础测试和服务 README。

## 8. 完成检查

- 代码未跨越服务边界，也未引入对其他服务私有模块的依赖。
- MySQL 中存在足够的持久事实支持重启恢复。
- 生产者使用发布确认，消费者手动 ACK、有限重试、DLQ 和幂等处理。
- 配置是类型化、允许列表化的，不存在任意环境变量修改接口。
- 示例不包含真实凭据、内网地址、签名 URL、模型权重或无授权资产。
- 相关测试、静态检查、Compose 校验和文档已经更新。
