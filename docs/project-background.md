# 项目背景与演进

## 来源

MediaFleet 由既有内部媒体服务的代码快照改造而来。旧服务最初围绕单体媒体剪辑和直播
录制业务持续演进，积累了视频处理、离线识别、ZLMediaKit 录制、对象存储和内容分析等
能力，也留下了服务职责混合、部署环境耦合、历史兼容代码较多和架构说明分散等问题。

MediaFleet 不延续旧仓库的 Git 历史，而是以独立 `main` 分支建立协作基线。这一选择便于
清理私有部署信息、凭据风险、内部材料和无再分发授权的二进制资产，也意味着后续变更
必须在本仓库重新建立清晰的设计记录和变更历史。

## 改造目标

- 将控制协调与媒体执行分离，使每种运行角色可以独立部署和扩缩容。
- 以 MySQL 保存分布式事实，以 RabbitMQ 承担可靠传输，消除对单进程内存状态的依赖。
- 保证录制命令始终到达拥有对应 ZLMediaKit 和录像目录的节点。
- 让同能力媒体 Worker 通过共享队列竞争消费，避免控制中心执行 FFmpeg 或加载 AI 模型。
- 用稳定契约连接 REST、SDK、CLI、MCP 和运维控制台，避免各入口绕过授权和审计。
- 清理内部环境信息，补齐许可证、安全、贡献、部署和扩展文档，使仓库适合 GitHub 协作。

## 继承与调整

当前代码仍保留一部分旧业务 API、兼容模型和处理器，目的是让改造过程可验证、可渐进。
“保留兼容”不表示继续扩展旧结构。新功能应优先进入 `media_platform` 的领域、契约和
应用层，以及职责明确的独立服务；旧兼容入口应逐步迁移到相同应用服务后再下线。

## 当前阶段

`0.1.x` 是内部预发布阶段。核心控制中心、录制节点、媒体 Worker、内容分析服务、
数据库基线和 RabbitMQ 可靠消费框架已经存在。接下来的重点是稳定远程接口、完成类型化
SDK 与 CLI、补齐真实基础设施集成测试，并继续减少旧兼容层。完成公开发布清单前，仓库
保持 Private。

仓库的实时进度以[项目状态](project-status.md)为准，计划方向以[路线图](roadmap.md)为准。
