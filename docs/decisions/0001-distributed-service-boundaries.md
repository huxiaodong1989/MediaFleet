# ADR-0001：建立分布式服务边界与持久事实模型

- 状态：已接受
- 日期：2026-09-28
- 决策者：MediaFleet 维护者

## 背景

原项目同时承载控制 API、录制、本地文件处理、通用媒体计算和 AI 能力。单进程状态、文件
所在地、模型资源和业务协调容易相互耦合，难以独立扩容，也难以在进程重启或多实例部署下
保证任务正确性。

## 决策

1. 将运行角色拆分为 `control-center`、`recorder-node`、`media-worker` 和可选的
   `content-analysis`。
2. 以 MySQL 保存节点、绑定、任务、投递状态和媒体产物等分布式事实。
3. 以 RabbitMQ 提供至少一次传输，并要求发布确认、手动 ACK、幂等、有限重试和 DLQ。
4. 录制命令定向到拥有 ZLMediaKit 和录像目录的节点；通用媒体任务由共享队列竞争消费。
5. 控制中心不执行 FFmpeg、不读取节点本地目录、不加载离线 ASR 或其他 AI 模型。
6. REST、后续 SDK、CLI、MCP 和运维控制台复用相同应用服务和安全边界。

## 影响

- 各运行角色可以按资源需求独立部署、升级和扩缩容。
- 每个跨服务流程都需要显式契约、幂等键、持久状态和故障恢复设计。
- 录制单元必须使用稳定身份并保证录像目录正确挂载。
- 新能力不能只以进程内状态实现，数据库和迁移设计成为功能的一部分。
- 运维复杂度提高，需要监控 MySQL、RabbitMQ、节点心跳、队列、DLQ 和执行租约。

## 备选方案

### 保持单体服务

部署简单，但媒体依赖、模型资源和控制 API 无法独立扩缩容，单进程故障影响面较大。

### 所有任务按节点定向

会降低通用任务的资源利用率并增加调度状态。只有必须访问节点本地资源的录制命令采用
定向队列，通用计算继续使用竞争消费。

### 仅依赖 RabbitMQ 或 Redis 保存任务状态

无法稳定支持业务查询、审计、恢复和条件状态迁移，因此拒绝作为权威事实来源。
